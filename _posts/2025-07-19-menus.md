Game UI systems in Rust require different considerations than web development. CSS handles styling and layout automatically, but game engines need explicit rendering, input handling, and cross-platform compatibility. This post covers the UI rendering system built for Mirador and how it implements the pause menu.

## Core Architecture

The UI system uses a modular, component-based approach. The `ButtonManager` class coordinates button functionality:

```rust
pub struct ButtonManager {
    pub buttons: HashMap<String, Button>,
    pub button_order: Vec<String>,
    pub text_renderer: TextRenderer,
    pub rectangle_renderer: RectangleRenderer,
    pub icon_renderer: IconRenderer,
    pub window_size: PhysicalSize<u32>,
    pub mouse_position: (f32, f32),
    pub mouse_pressed: bool,
    pub just_clicked: Option<String>,
    pub container_rect: Option<Rectangle>,
    pub last_mouse_position: (f32, f32),
    pub last_mouse_pressed: bool,
}
```

This design separates rendering concerns. Each renderer handles specific visual elements while the manager coordinates input and state. The system tracks mouse state to avoid unnecessary updates and uses ordered button lists for consistent rendering.

### Positioning System

The positioning system uses anchor points instead of hardcoded coordinates:

```rust
#[derive(Debug, Clone)]
pub struct ButtonPosition {
    pub x: f32,
    pub y: f32,
    pub width: f32,
    pub height: f32,
    pub anchor: ButtonAnchor,
}

#[derive(Debug, Clone, Default)]
pub enum ButtonAnchor {
    TopLeft,
    #[default]
    Center,
}
```

The `calculate_actual_position()` method converts anchored coordinates to top-left rendering coordinates:

```rust
pub fn calculate_actual_position(&self) -> (f32, f32) {
    let actual_x = match self.anchor {
        ButtonAnchor::TopLeft => self.x,
        ButtonAnchor::Center => self.x - self.width / 2.0,
    };

    let actual_y = match self.anchor {
        ButtonAnchor::TopLeft => self.y,
        ButtonAnchor::Center => self.y - self.height / 2.0,
    };

    (actual_x, actual_y)
}
```

This makes layout calculations more intuitive - positioning a button at screen center doesn't require manual offset calculations.

### Spacing Strategies

The system supports different spacing approaches:

```rust
#[derive(Debug, Clone, PartialEq)]
pub enum ButtonSpacing {
    Wrap,
    Hbar(f32),
    Tall(f32),
```

- `Wrap`: Button size matches text content
- `Hbar(f32)`: Button width proportional to container width
- `Tall(f32)`: Button height proportional to container height

This flexibility handles both compact layouts and structured grid interfaces.

### Rounded Corners with Signed Distance Functions

The rounded corners use Signed Distance Functions (SDFs) for smooth, anti-aliased rendering. An SDF returns the shortest distance from any point to a shape's surface, with positive values outside the shape and negative values inside.

The rectangle shader implements an SDF for rounded rectangles:

```rust
fn sdf_rounded_rect(p: vec2<f32>, size: vec2<f32>, radius: f32) -> f32 {
    let half_size = size * 0.5;
    let d = abs(p - half_size) - half_size + radius;
    return length(max(d, vec2<f32>(0.0))) + min(max(d.x, d.y), 0.0) - radius;
}
```

This function calculates distance to the rectangle edge, then applies corner radius. The fragment shader uses this distance to determine pixel opacity:

```rust
@fragment
fn fs_main(in: VertexOutput) -> @location(0) vec4<f32> {
    if (in.corner_radius <= 0.0) {
        return in.color;
    }

    let distance = sdf_rounded_rect(in.uv, in.rect_size, in.corner_radius);
    let alpha = 1.0 - smoothstep(-1.0, 1.0, distance);

    var output_color = in.color;
    output_color.a *= alpha;

    return output_color;
}
```

The `smoothstep` function creates anti-aliasing that eliminates jagged edges. This approach provides resolution-independent rendering that scales well across different display densities.

### State Management

Buttons maintain a `ButtonState` that changes based on user interaction. The renderer selects colors and effects based on this state. The system only updates states when mouse position or press state actually changes, preventing unnecessary rendering operations.

For upgrade menu buttons, we implement subtle scaling effects - buttons grow slightly on hover and shrink when pressed. This provides immediate visual feedback without being distracting.

## Pause Menu Implementation

The pause menu demonstrates how the architectural components work together. It provides a clean overlay when the game is paused, offering options for continuing, restarting, or exiting.

### Menu Structure

The menu defines actions using an enum for type safety:

```rust

    Restart,
    QuitToMenu,
    QuitApp,

    None,
```

### Responsive Design

The menu implements responsive scaling based on screen resolution:

```rust
fn create_menu_buttons(button_manager: &mut ButtonManager, window_size: PhysicalSize<u32>) {
    let reference_height = 1080.0;
    let scale = (window_size.height as f32 / reference_height).clamp(0.7, 2.0);

    let button_width = (window_size.width as f32 * 0.38 * scale).clamp(180.0, 600.0);
    let button_height = (window_size.height as f32 * 0.09 * scale).clamp(32.0, 140.0);
    let button_spacing = (window_size.height as f32 * 0.015 * scale).clamp(2.0, 24.0);

    let total_height = button_height * 5.0 + button_spacing * 4.0;
    let center_x = window_size.width as f32 / 2.0;
    let start_y = (window_size.height as f32 - total_height) / 2.0;
}
```

This ensures the menu looks appropriate across different screen sizes while maintaining usability.

### Semantic Styling

The menu uses semantic button styles to communicate purpose:


Each style function creates consistent designs with appropriate colors for different action types.

### Button Positioning

Buttons are positioned using a helper function for vertical spacing:

## The Pause Menu in Detail

The pause menu serves as a practical example of how the UI system components work together. It's a relatively simple interface that demonstrates the system's capabilities without overwhelming complexity.

### Menu Structure and Layout

The pause menu consists of five main buttons arranged vertically in the center of the screen. The layout is calculated dynamically based on window size, ensuring the menu remains properly positioned and sized regardless of resolution.

The menu includes:
- **Resume Game**: Primary action to continue the current session
- **Restart Run**: Restarts the current game session

There's also a small debug button positioned in the bottom-left corner that toggles debug information display.

### State Management and Visibility

The pause menu manages its own visibility state and integrates with the game's pause system:

```rust
pub fn show(&mut self, is_test_mode: bool) {
    self.visible = true;
    self.last_action = PauseMenuAction::None;

    for button in self.button_manager.buttons.values_mut() {
        button.set_visible(true);
    }

    self.update_test_mode_button_text(is_test_mode);
}

pub fn hide(&mut self) {
    self.visible = false;
    self.last_action = PauseMenuAction::None;

    for button in self.button_manager.buttons.values_mut() {
        button.set_visible(false);
    }
}
```

When the menu is hidden, all buttons become invisible and non-interactive, preventing them from interfering with game input.

### Dynamic Content Updates

The menu adapts its content based on the game's current state. The Test Mode button text changes to reflect whether test mode is currently active:

```rust
pub fn update_test_mode_button_text(&mut self, is_test_mode: bool) {
    if let Some(button) = self.button_manager.get_button_mut("toggle_test_mode") {
        let new_text = if is_test_mode {
            "Disable Test Mode"
        } else {
            "Toggle Test Mode"
        };

        button.text = new_text.to_string();
        self.button_manager.text_renderer.update_text(&button.text_id, new_text);
    }
}
```

This provides immediate feedback to the user about the current state without requiring them to remember previous actions.

### Window Resize Handling

The menu handles window resize events gracefully by recreating buttons with new dimensions:

```rust
pub fn resize(&mut self, queue: &Queue, resolution: Resolution) {
    self.button_manager.resize(queue, resolution);
    self.recreate_buttons_for_new_size();
}

fn recreate_buttons_for_new_size(&mut self) {
    let window_size = self.button_manager.window_size;

    self.button_manager.buttons.clear();
    self.button_manager.button_order.clear();

    Self::create_menu_buttons(&mut self.button_manager, window_size);

    if self.visible {
        for button in self.button_manager.buttons.values_mut() {
            button.set_visible(true);
        }
    }
}
```

This ensures the menu remains properly laid out and functional when the window size changes.

## Rendering Pipeline

The rendering system uses a layered approach:

```rust
pub fn render(
    &mut self,
    device: &Device,
    render_pass: &mut RenderPass,
) -> Result<(), glyphon::RenderError> {
    self.rectangle_renderer.clear_rectangles();

    if let Some(container_rect) = &self.container_rect {
        self.rectangle_renderer.add_rectangle(container_rect.clone());
    }

    for button_id in &self.button_order {
        if let Some(button) = self.buttons.get(button_id) {
            if button.visible {
                let (actual_x, actual_y) = button.position.calculate_actual_position();
                let color = match button.state {
                    ButtonState::Normal => button.style.background_color,
                    ButtonState::Hover => button.style.hover_color,
                    ButtonState::Pressed => button.style.pressed_color,
                    ButtonState::Disabled => button.style.disabled_color,
                };

                let rectangle = Rectangle::new(actual_x, actual_y, button.position.width, button.position.height, color_array)
                    .with_corner_radius(button.style.corner_radius);

                self.rectangle_renderer.add_rectangle(rectangle);
            }
        }
    }

    self.rectangle_renderer.render(device, render_pass);
    self.icon_renderer.render(device, render_pass);
    self.text_renderer.render(render_pass)
}
```

This renders backgrounds first, then icons, then text, ensuring proper layering.

## Performance Considerations

The system includes several optimizations:

1. **State Change Detection**: Only updates button states when mouse position or press state actually changes
2. **Layered Rendering**: Each renderer type is optimized for its specific content
3. **DPI Scaling**: Text and UI elements scale appropriately for high-DPI displays
4. **Efficient Hit Testing**: Button bounds are calculated once and cached

## Conclusion

The UI system provides a foundation for responsive game interfaces. The modular architecture supports adding new components while maintaining consistent styling. The pause menu shows how these components work together to create a functional interface that scales across different screen sizes.

The key is separation of concerns between positioning, styling, input handling, and rendering. Each component has a clear responsibility, making the codebase maintainable. The SDF-based rendering provides clean visuals, while the modular architecture ensures extensibility.

As we continue developing Mirador, this architecture will support more complex UI features while maintaining performance standards. The combination of mathematical precision in rendering, state management, and responsive design creates a UI system that works reliably across different devices and resolutions.
